# Birthday Games

Мини-сервис учёта баллов для игр на дне рождения. Гости смотрят рейтинг и
правила игр, администратор вносит результаты через скрытую страницу `/adminka`
(без авторизации — see "Adminka" ниже).

## Стек

- Next.js 14 (App Router) + TypeScript
- Prisma + SQLite
- Tailwind CSS

## Быстрый старт

```bash
npm install
cp .env.example .env
npm run db:push   # создать таблицы
npm run db:seed   # засеять 14 игроков и примеры игр
npm run dev
```

Сайт: `http://localhost:3000`
Админка: `http://localhost:3000/adminka`

## Запуск на вечеринке (локальная Wi-Fi сеть)

```bash
npm run build
npm run start -- -H 0.0.0.0 -p 3000
```

Затем зайти с любого телефона в той же Wi-Fi сети по адресу
`http://<локальный-IP-компьютера>:3000`.

## Деплой на shared-хостинг с ISPmanager (Node.js-приложение)

ISPmanager запускает Node.js-приложения через встроенный PM2 (бинарники под
`/usr/lib/ispnodejs/`) и проксирует домен через nginx на **unix-сокет**
(`/var/www/<user>/data/nodejs/<n>.sock`), а не на TCP-порт — поэтому обычный
`next start` не подходит напрямую. В проекте есть `server.js` (команда `npm
run start:passenger`), который оборачивает Next.js в свой http-сервер и умеет
слушать как порт, так и unix-сокет — смотря что придёт в `process.env.PORT`.

Если у вашего аккаунта ISPmanager нет видимого раздела «Node.js» для домена
(бывает при ограниченных правах), приложение всё равно можно запустить и
управлять им напрямую через pm2 по SSH — команды ниже это учитывают.

1. **По SSH**, из корневой директории домена:

   ```bash
   git clone <URL-репозитория> .        # или загрузите код файловым менеджером
   npm install
   cp .env.example .env
   ```

   В `.env` укажите путь к SQLite-файлу вне директории, которую перезаписывает
   деплой (иначе база будет теряться при каждом обновлении кода), например:

   ```
   DATABASE_URL="file:/var/www/<user>/data/birthday-games.db"
   ```

   Дальше:

   ```bash
   npx prisma db push   # создать таблицы по этому DATABASE_URL
   npm run db:seed      # засеять 14 игроков и примеры игр
   npm run build        # next build (нужен перед запуском в production)
   ```

2. **Узнайте порт/сокет**, который ждёт nginx для вашего домена:

   ```bash
   grep -i -E "proxy_pass|listen" /etc/nginx/vhosts/<user>/<домен>.conf
   ```

   Обычно там будет строка вида `proxy_pass http://unix:/var/www/<user>/data/nodejs/0.sock;`.

3. **Запустите приложение через pm2** (важно передать именно этот путь в
   `PORT` — `server.js` сам определит, что это сокет, а не номер порта):

   ```bash
   PM2="/usr/lib/ispnodejs/bin/node /usr/lib/ispnodejs/lib/node_modules/pm2/bin/pm2"

   sudo -u <user> HOME=/var/www/<user>/data PORT=/var/www/<user>/data/nodejs/0.sock \
     $PM2 start server.js --name <домен> --interpreter /usr/lib/ispnodejs/bin/node \
     --cwd /var/www/<user>/data/www/<домен>

   sudo -u <user> HOME=/var/www/<user>/data $PM2 save
   ```

   ⚠️ Если раздел «Node.js» в ISPmanager для этого домена уже был создан
   раньше (даже если он вам не виден в интерфейсе) — **обязательно** сначала
   проверьте `pm2 list` и убедитесь, что там нет старого процесса с
   неправильной командой запуска (например `npm run build` вместо `start` —
   это заставляет pm2 бесконечно перезапускать процесс, который тут же
   завершается, и параллельные сборки начинают ломать друг друга). Такой
   процесс нужно удалить (`pm2 delete <id>`) перед тем, как поднимать новый.

4. После каждого обновления кода на сервере: `git pull`, `npm install` (если
   менялись зависимости), `npm run build`, затем
   `sudo -u <user> HOME=/var/www/<user>/data $PM2 restart <домен>`.

⚠️ SQLite нормально работает на обычном сервере с постоянным диском (в
отличие от serverless-платформ вроде Vercel, где база обнулялась бы между
вызовами) — на этом хостинге дополнительных телодвижений не нужно, важно
только держать файл БД вне пересобираемой директории (см. шаг 2).

⚠️ **Важно про `/adminka`**: пока сайт был доступен только в локальной Wi-Fi
сети на вечеринке, защита «через неизвестность» была разумным компромиссом.
На реальном домене `/adminka` теоретически может найти кто угодно в интернете
(перебором, через логи, через случайную ссылку и т.д.). Если админка будет
жить дольше одного вечера — стоит закрыть её хотя бы паролем на уровне
хостинга (в ISPmanager это обычно раздел «Защищённые директории» на домене)
или добавить Basic Auth прямо в приложение. Могу добавить второе по запросу.

## Adminka

`/adminka` — без пароля и без ссылок из публичного интерфейса (защита "через
неизвестность", осознанный компромисс для скорости, см. ТЗ). Страница закрыта
от индексации через `robots.txt` (`Disallow: /adminka`) и мета-тег
`robots: noindex`.
